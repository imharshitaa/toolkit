ToolKit

A command-line framework for deploying, scanning, and reporting across open-source security tooling — no third-party SaaS credentials required.

One CLI drives real security tools — Splunk, Wazuh, OWASP ZAP, nmap, Trivy, plus two pure-Python static scanners — through a single consistent deploy / scan / report interface. Every result is backed by real tool output, persisted to disk, and rendered into an HTML or Markdown report.

01 Overview

      

        

          
What ToolKit does

          
ToolKit is a single CLI (toolkit) that drives real security tools through
            one consistent interface. Instead of juggling five different tool invocations and five
            different report formats, a security engineer runs the same four verbs —
            deploy, scan, report, open — against
            any supported domain and tool, and gets back a persisted, real result every time.

          
The CLI also catalogs roughly 19 enterprise security products (CrowdStrike, Microsoft
            Sentinel, AWS GuardDuty, Tenable, Qualys, and others) for domain-coverage reference via
            toolkit list-tools. Those are commercial SaaS products by definition and
            require the vendor's own account — so they're listed for context, not reimplemented.

        

        

          
The problem it solves

          
Standing up a local SOC/AppSec/NetSec lab usually means learning five separate tool
            CLIs, five separate output formats, and writing one-off glue scripts to turn raw tool
            output into something reviewable. ToolKit collapses that into one command surface:
            spin up Splunk or Wazuh, run a ZAP scan against a local target, sweep a subnet with
            nmap, scan a container image with Trivy, or statically audit Terraform / Docker Compose
            and LLM transcripts for common misconfigurations — all through the same interface,
            all producing a report from the same pipeline.

          
Who it's for: security engineers who want one CLI to
            drive a local security lab without re-learning tooling for every domain.

03 Architecture

      
A thin CLI layer routes to a shared core engine, which
        dynamically loads per-tool modules built on common infrastructure.


      

        

          

            
            
            
            architecture.txt
          

          
toolkit/cli.py          ← click command group (version, status, list-tools)
  ├── toolkit/deploy.py  ← `toolkit deploy <module> <tool>`
  ├── toolkit/scan.py    ← `toolkit scan <module> <tool>` (--simulate for attack sims)
  ├── toolkit/report.py  ← `toolkit report <module> <tool>`
  └── toolkit/open_dashboard.py  ← `toolkit open <module> <tool>`
        │
        ▼
  toolkit/core.py (ToolKitCore)
    - dynamically imports modules.<DOMAIN>.<tool>.<operation>
    - every operation module exposes execute(**kwargs) -> bool
        │
        ▼
  modules/<DOMAIN>/<tool>/
    config.py    ← settings + validate()
    deploy.py    ← for tools with a deployable backend
    scan.py       } one or more operations, each calling
    simulate.py   } toolkit.state.save_result() on completion
    report.py    ← thin wrapper: load_latest_result() + render_report()
        │
        ▼
  Shared infrastructure (toolkit/):
    security.py   ← require_authorized_target() — blocks active scans/sims
                    against anything outside RFC1918 + loopback unless
                    --i-have-authorization is passed
    state.py      ← persists every run's result to .toolkit_state/*.json
    reporting.py  ← renders persisted state into HTML or Markdown

        


        

          

            
CLI layer

            
A Click command group exposes version, status,
              list-tools, and the four verbs — deploy, scan,
              report, open — each a thin entry point into the core.

          

          

            
Core engine

            
ToolKitCore dynamically imports modules.<DOMAIN>.<tool>.<operation>
              — every operation module exposes a single execute(**kwargs) -> bool
              contract, so adding a tool means adding a module, not touching the core. If an
              operation module doesn't exist for a tool (e.g. a bare scan for Splunk,
              which only has simulate.py), the import fails and the command reports
              an error — the console below reproduces that exact failure path.

          

          

            
Modules

            
Each modules/<DOMAIN>/<tool>/ directory owns its
              config.py, deploy.py, scan.py /
              simulate.py, and report.py — plus its own README with
              tool-specific configuration and usage.

          

          

            
Shared infrastructure

            
security.py enforces the authorization guardrail,
              state.py persists every run's result to .toolkit_state/,
              and reporting.py renders that persisted state into HTML or Markdown.

06 Features

      

        

          ⇪
          
Deploy

          
Stand up a tool's backend — Docker Compose stacks for Splunk/Wazuh/ZAP, or
            cloud/Kubernetes paths using your own credential chain. --dry-run is
            supported for a no-op preview.

        

        

          ◎
          
Scan

          
Run a real scan — nmap sweep, Trivy image/filesystem scan, ZAP spider + active scan,
            or a static IaC/LLM-transcript audit — and persist the structured result.

        

        

          ▤
          
Report

          
Render the most recent real result for a tool into an HTML or Markdown report, with
            optional severity filtering. No result on disk means a clear error, never a
            placeholder.

        

        

          ⛨
          
Security guardrails

          
Active scans and simulations are blocked against anything outside loopback + RFC1918
            private ranges by default — --i-have-authorization is required, and even
            then it's logged loudly. Try it in the checker below.

        

        

          ⌂
          
Local-first execution

          
No embedded credentials, no hosted backend, no telemetry. Cloud paths use your own
            AWS/Kubernetes credential chain, exactly like the AWS CLI or kubectl
            themselves.

        

      

    

  


  
  

    

      
07 Security Model

      

        

          
Authorization checks

          
toolkit/security.py::require_authorized_target blocks nmap/ZAP/Trivy-image
            scans and Splunk attack simulations against anything outside loopback + RFC1918
            private ranges unless --i-have-authorization is passed explicitly — and
            even then it logs a loud warning. Only test systems you own or hold written permission
            to assess.

        

        

          
Credential handling

          
No embedded credentials, anywhere. AWS/Azure/GCP credentials are read strictly from
            environment variables / the standard credential chain
            (toolkit/utils.py::get_cloud_credentials) — never hardcoded, never stored
            by ToolKit. Lab files require every password/token/CIDR as an explicit input with no
            built-in defaults.

        

        

          
Safe scanning

          
Results aren't fabricated — toolkit report reads the real persisted
            result of the most recent run, or fails clearly if none exists. ZAP/nmap/Trivy output
            is parsed defensively, subprocess calls have explicit timeouts, and the IaC Auditor /
            LLM Risk Scanner are documented as heuristic pattern matchers, not certified
            detection.

        

      


      

        
Try the authorization guardrail

        
This reimplements the private/loopback check from
          toolkit/security.py client-side — the same RFC1918 + loopback ranges, the
          same pass/block logic. It does not resolve hostnames via DNS the way the
          real socket.gethostbyname call does, so only literal IPs, CIDRs, and
          localhost are evaluated here; arbitrary hostnames fall through to "cannot
          verify client-side."

09 Limitations

      
Documented explicitly rather than silently skipped — this
        section exists to draw a hard line between what runs today and what is cataloged for
        reference.


      

        

          
Implemented vs. catalog-only

          

            

          

        


        

          
Known limitations

          
    
            
  • nmap / Trivy binaries — not installed in every environment. Unit
              tests mock subprocess/shutil.which; real binary output is
              covered by parser tests, not a live scan.
    • 
            
  • Docker-dependent live deploys (ZAP daemon, Wazuh stack, Splunk
              Docker deployment) require a working Docker daemon — covered by mocked integration
              tests where Docker isn't available.
    • 
            
  • Full Splunk/Wazuh stacks are multi-GB and slow to bring up —
              covered by dry-run + mocked tests, not a live full-stack deployment in CI.
    • 
            
  • Live AWS/Kubernetes deploys require the operator's own
              cloud/cluster credentials, which this project does not have or store. The code paths
              are present and readable, not exercised against a real account here.
    • 
            
  • toolkit scan --output is accepted by the CLI but
              unused — every module persists its result via toolkit/state.py
              regardless. Use toolkit report to get output.
    • 
            
  • This website — the console above simulates CLI output text; it
              does not install binaries, spawn containers, or touch a network. Every "supported
              operation" and flag shown is read from the real source, not guessed.
    •
